# Sessions, rulings, and the canon ledger

How a working session with the workshop partner opens, runs, and closes, and how decisions are made and kept. Entry format is described in `../README.md`.

---

### Roles

**What.** The workshop partner proposes; the author rules. Nothing is written into the planning documents until ruled. The author writes the prose.

**When.** Always.

**How.** The partner's job is to think alongside the author: surface implications, ask the right questions, make connections, push back when something does not cohere. The author values genuine engagement over agreement. The partner delivers beat specs, catechisms, examinations against a discipline, and modification lists; never finished prose, never a redraft of the author's prose. Follow the author's lead on what phase the work is in; do not push toward prose while foundations are being built.

**Origin.** Reptile House `CLAUDE.md` (March 2026); Kestrel session protocol (August 28 2026, after a false start that had to be reverted).

**Scope.** General to this collaboration.

---

### The session opens and stops

**What.** A session opens by reading the handoff file and the notes file at the frontier, then stops for a state summary and conversation before anything is written.

**When.** Every session.

**How.** Read first, in the order the handoff lists. Summarize where things stand and what the next work is. Wait. The false start that produced this rule was a session that read the handoff and began deriving.

**Origin.** Kestrel Book 4, August 28 2026.

**Scope.** General.

---

### The session-close checklist

**What.** A fixed list run at the end of every sitting.

**When.** Every sitting, including short ones.

**How.**

0. Prose notes from the sitting are in the review queue, not in chat; the chat carried only the feel read.
1. Fold every decision made in the sitting into the owning document. Never leave it only in chat.
2. Update the outline and the notes file together for any beat touched; run the sync check; it must print nothing. Re-run the presence audit if beats changed.
3. Rewrite the handoff's *Where things stand* and *Next work* blocks; move any ledger item ruled this sitting to *Resolved*; add any new question with the event that first needs it; date the closing line.
4. Commit and push.

**Origin.** Kestrel Book 4, August–September 2026.

**Scope.** General.

### The canon ledger

**What.** Open canon questions are ruled just in time, when the first beat that needs each one is derived, and ruled at book scale. There is no canon-settlement sitting.

**When.** Any project with open world or character questions, which is every project.

**How.** The ledger is a list in the handoff, sorted by the first event that needs each item. The rule: nothing is beaten on an unruled item it depends on; each item is ruled inside the derivation of the first beat that forces it. Before ruling, walk the event list for every place the answer touches, then fold the ruling into the owning reference document the same sitting. Never "rule X and Y first, then derive." Keep a *Resolved* record so nothing is re-litigated. Items may be reopened by later beats; that is expected. Items no beat depends on are marked "rule when convenient."

Why the settlement sitting was retired: beat work generates and revises canon regardless; a sitting rules against imagined pressure and gets re-ruled against real pressure.

**Origin.** Kestrel Book 4, August 28 2026, replacing a planned canon-settlement step.

**Scope.** General.

---

### Ask rather than confabulate

**What.** Flag uncertain ground about characters, relationships, or setting. Never assert an unverified cause.

**When.** Always, and especially when reasoning about a character instead of looking them up.

**How.** Before reviewing or deriving anything involving a character with a canon entry, read the entry. Three separate errors in one Kestrel sitting came from reasoning about the narrator instead of looking him up, twice past canon already on the page. When a fact is not in the documents, say so and ask, or mark the proposal as unratified. A proposal is one thing; a ruling is another; the documents distinguish them.

**Origin.** Both projects; sharpened in Kestrel, August 30–31 2026.

**Scope.** General.

---

### Rulings are logged and dropped

**What.** Once the author rules on a suggestion, explicitly or by declining to act, log the ruling with the reasoning and drop the item. Never carry declined items forward in a pending list. Never re-raise.

**When.** Every suggestion, every review note, every moment proposal.

**How.** The log entry says what was proposed, what was ruled, and why, in the document that owns the subject (the review queue, the moment trove, the notes file). A declined idea that would be re-proposed in a different form is marked "not to be re-raised in any form." Superseded versions of an accepted idea are recorded in one line "so it is not re-proposed."

**Origin.** Kestrel Book 4, September 2026; also held in the partner's persistent memory.

**Scope.** General.

### Pause for worldbuilding on demand

**What.** When a run of beats calls for it, beat work stops and the session looks more closely at the society, place, or system the beats need.

**When.** Whenever derivation keeps tripping over an unbuilt part of the world.

**How.** Question by question; findings go into the setting file as they are made; system-wide facts are upstreamed to the shared setting repository. The handoff names the likely next trigger ("event 5's custody mechanics look like the next trigger").

**Origin.** Kestrel Book 4, standing policy, August 26 2026.

**Scope.** General.

---

### The prose-time decisions log

**What.** While the author drafts between sittings, decisions settled at the keyboard are logged one line each in the handoff, for folding into the notes files at the next sitting.

**When.** Whenever the author is drafting from derived beats and the beats carry open levers.

**How.** Format: beat key, then what was decided. The next sitting folds each line into its notes file and strikes it. Open decisions inside derived beats are called *prose-time levers* and are listed so the author knows which choices are theirs to make at the keyboard.

**Origin.** Kestrel Book 4, August 28 2026.

**Scope.** General.

---

### Standing warnings

**What.** A block in the handoff listing corrections that must not regress: dead images, superseded names, stale claims in shared notes, generated numbers wrongly promoted.

**When.** Whenever a correction has been made once and the wrong version still exists somewhere readable.

**How.** One line per warning, naming the wrong version and the right one. Read with the handoff every session.

**Origin.** Kestrel Book 4, August 27 2026.

**Scope.** General.

---

### Persistent memory

**What.** The workshop partner keeps a persistent memory of the author's rulings and preferences, so that corrections are made once.

**When.** Any ruling about how to work, as opposed to what is true in the book.

**How.** Rulings about the book go into the book's documents. Rulings about the method (never redraft; never flag colloquial grammar in dialogue; a question ending in a period is tonal) go into memory as well, because they apply across projects. This tools project is the durable, author-readable form of the same rulings.

**Origin.** Both projects.

**Scope.** General to this collaboration.
